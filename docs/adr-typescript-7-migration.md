# ADR: TypeScript 7 migration

[日本語](adr-typescript-7-migration_ja.md)

- Status: accepted for implementation
- Decision date: 2026-07-25
- Related issue: [#32](https://github.com/yaona807/virune/issues/32)
- Failed direct upgrade: [#26](https://github.com/yaona807/virune/pull/26)

## Context

Virune uses TypeScript in two distinct roles:

1. the repository build compiler invoked through `tsc -b`;
2. the synchronous Compiler API embedded by `@virune/js-interop` to resolve JavaScript and TypeScript declarations at runtime.

TypeScript 7 is a native compiler and language server. Version 7.0 intentionally does not expose the existing JavaScript Compiler API. The TypeScript team publishes `@typescript/typescript6` for tools that still require that API and documents running it side-by-side with the native TypeScript 7 compiler.

A direct root dependency update from TypeScript 6.0.3 to 7.0.2 in PR #26 failed all build-oriented workflows. That update replaced the package imported as `typescript`, so the repository lost the JavaScript API required by the interop provider while also changing the build toolchain in one step.

References:

- [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- [TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

## Compiler API inventory and boundary

The canonical inventory is generated by:

```bash
npm run typescript:boundary:check
```

Production Compiler API imports are restricted to `packages/js-interop/`. The current implementation is centered on `packages/js-interop/src/index.ts`, where the provider uses `Program`, `TypeChecker`, `LanguageService`, module resolution, diagnostics, and TypeScript AST predicates. Tests under the same package may import TypeScript to construct controlled fixtures.

No compiler, runtime, CLI, formatter, standard-library, language-server, or VS Code package may import the `typescript` JavaScript API directly. The boundary verifier rejects new imports or package dependencies outside the approved package.

## Decision

Use separate packages for the build compiler and embedded Compiler API.

The migration PR will use the following exact dependency shape:

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@7.0.2",
    "typescript": "npm:@typescript/typescript6@6.0.3"
  }
}
```

`@typescript/native` supplies the native `tsc` executable used by repository build scripts. The `typescript` import specifier continues to resolve to the TypeScript 6 compatibility package for `@virune/js-interop`. The interop workspace must retain the same exact alias so its published dependency graph is explicit and does not depend on npm hoisting.

Versions are exact rather than ranged:

- the native compiler is upgraded through a reviewed dependency PR with full CI and stable-release evidence;
- the compatibility API is upgraded independently and requires binding-corpus review;
- the two versions are not required to share a release cadence;
- TypeScript 7.1 or later cannot replace the compatibility API until its programmatic API is evaluated against the Virune provider contract.

## Prototype gate

The prototype runs without modifying the committed dependency graph:

```bash
npm run prototype:typescript7
```

It installs the exact TypeScript 7 compiler into an isolated temporary tool directory and then verifies:

1. the TypeScript 6 Compiler API boundary and version;
2. a forced clean build with TypeScript 6;
3. a forced clean build with TypeScript 7;
4. byte-for-byte equality of emitted JavaScript, declarations, and maps, excluding `.tsbuildinfo`;
5. an incremental TypeScript 7 build that does not mutate emitted output;
6. `@virune/js-interop` tests and the binding corpus;
7. language-server and VS Code extension tests;
8. VSIX packaging.

Evidence is written to `.cache/typescript-7-prototype/` as JSON, Markdown, and per-command logs. The dedicated GitHub Actions workflow uploads the evidence on success or failure.

## Migration sequence

1. Keep the current TypeScript 6 dependency graph while the prototype gate is maintained.
2. Review prototype output and diagnostic parity on Linux.
3. Open the implementation PR that applies the two-package dependency shape and updates the lockfile.
4. Run the normal operating-system matrix, browser conformance, performance, VSIX smoke, binding corpus, release dry run, and reproducible release gate.
5. Review compiler output, diagnostics, clean and incremental timings, package size, and startup behavior.
6. Merge only if all existing release gates and the TypeScript 7 prototype pass.
7. Remove the prototype-only installation step after the committed toolchain uses TypeScript 7; retain the boundary policy and parity checks.

## Rollback

Rollback is a single dependency change: remove `@typescript/native`, restore `typescript` to exact `6.0.3`, regenerate the lockfile, and run the stable release gate. The Compiler API import boundary does not change during rollback.

## Consequences

- Virune can use the native compiler without rewriting the synchronous interop provider.
- Compiler build performance and Compiler API compatibility can be upgraded independently.
- The repository temporarily carries two TypeScript implementations.
- Package size and install time may increase because native platform packages and the compatibility API coexist.
- The boundary policy prevents accidental coupling to the legacy API outside JavaScript interop.
