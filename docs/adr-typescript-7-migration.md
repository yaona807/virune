# ADR: TypeScript 7 migration

[日本語](adr-typescript-7-migration_ja.md)

- Status: accepted for implementation
- Decision date: 2026-07-25
- Related issue: [#32](https://github.com/yaona807/virune/issues/32)
- Failed direct upgrade: [#26](https://github.com/yaona807/virune/pull/26)

## Context

Virune uses TypeScript in two distinct roles:

1. the repository build compiler invoked through `tsc -b`;
2. the synchronous Compiler API used by JavaScript interoperability and declaration binding.

TypeScript 7 is a native compiler and language server. Version 7.0 intentionally does not expose the existing JavaScript Compiler API. The TypeScript team publishes `@typescript/typescript6` for tools that still require that API and documents running it side-by-side with the native TypeScript 7 compiler.

A direct root dependency update from TypeScript 6.0.3 to 7.0.2 in PR #26 failed all build-oriented workflows. That update replaced the package imported as `typescript`, so the repository lost the JavaScript API required by its API consumers while also changing the build toolchain in one step.

References:

- [Announcing TypeScript 7.0](https://devblogs.microsoft.com/typescript/announcing-typescript-7-0/)
- [TypeScript Compiler API](https://github.com/microsoft/TypeScript/wiki/Using-the-Compiler-API)

## Compiler API inventory and boundary

The canonical inventory is generated by:

```bash
npm run typescript:boundary:check
```

Production API consumers are:

- `packages/js-interop/`, including the runtime provider, adapter, and controlled tests. The provider uses `Program`, `TypeChecker`, `LanguageService`, module resolution, diagnostics, and AST predicates.
- `packages/cli/src/bind.ts`, which parses TypeScript declarations and converts supported functions, interfaces, aliases, and variables into Virune bindings.

Repository tooling consumers are restricted to:

- `scripts/probe-typescript-7.mjs`, which uses the compatibility API to compare declaration output semantically;
- `scripts/run-binding-corpus.mjs`, which records the TypeScript version in corpus evidence;
- `scripts/verify-public-abi.mjs`, which analyzes declaration output while enforcing the public ABI snapshot.

The root, CLI, and JavaScript interop manifests currently declare TypeScript. No compiler, runtime, formatter, standard-library, language-server, VS Code, or unrelated tooling source may add a Compiler API import or dependency. The machine-readable policy rejects changes outside the enumerated roots, paths, and manifests.

## Decision

Use separate packages for the build compiler and embedded Compiler API.

The root migration will use the following exact dependency shape:

```json
{
  "devDependencies": {
    "@typescript/native": "npm:typescript@7.0.2",
    "typescript": "npm:@typescript/typescript6@6.0.3"
  }
}
```

Both API-consuming workspaces will use the exact compatibility alias:

```json
{
  "dependencies": {
    "typescript": "npm:@typescript/typescript6@6.0.3"
  }
}
```

`@typescript/native` supplies the native `tsc` executable used by repository build scripts. The `typescript` import specifier continues to resolve to the TypeScript 6 compatibility package for the interop provider, CLI binder, and approved tooling. Explicit workspace dependencies prevent runtime behavior from depending on npm hoisting.

Versions are exact rather than ranged:

- the native compiler is upgraded through a reviewed dependency PR with full CI and stable-release evidence;
- the compatibility API is upgraded independently and requires binding-corpus and ABI review;
- the two versions are not required to share a release cadence;
- TypeScript 7.1 or later cannot replace the compatibility API until its programmatic API is evaluated against both the interop provider and binding generator contracts.

## Prototype gate

The prototype runs without modifying the committed dependency graph:

```bash
npm run prototype:typescript7
```

It installs the exact TypeScript 7 compiler into an isolated temporary tool directory and then verifies:

1. the TypeScript 6 Compiler API inventory, boundary, and version;
2. a forced clean build with TypeScript 6;
3. a forced clean build with TypeScript 7;
4. byte-for-byte equality of emitted JavaScript and semantic equality of emitted declarations, excluding `.tsbuildinfo`;
5. source-map equality for version, output file, source root, source files, and embedded source content, while recording reviewed name or mapping differences;
6. an incremental TypeScript 7 build that does not mutate emitted output;
7. `@virune/js-interop` tests and the binding corpus;
8. language-server and VS Code extension tests;
9. VSIX packaging.

The prototype compares declaration files through the TypeScript 6 compatibility AST. It normalizes string-literal quote style, redundant `undefined` in optional `unknown` members or parameters, and a local `typeof` reference when it resolves to the same declared function type. Any other declaration difference remains blocking.

The initial prototype produced identical JavaScript across 512 emitted files. Four declarations differed textually but were semantically equivalent: two quote-style changes, optional `unknown | undefined` simplified to `unknown`, and inferred aliases printed as `typeof` references to the same local function declarations. It also identified 84 source maps whose source structure was unchanged but whose generated mapping encoding differed. These reviewed differences are retained as explicit evidence rather than treated as unreviewed code-output changes.

Evidence is written to `.cache/typescript-7-prototype/` as JSON, Markdown, and per-command logs. The dedicated GitHub Actions workflow uploads the evidence on success or failure.

## Migration sequence

1. Keep the current TypeScript 6 dependency graph while the prototype gate is maintained.
2. Review prototype output and diagnostic parity on Linux.
3. Open the implementation PR that applies the native compiler alias and compatibility aliases to the root, CLI, and JavaScript interop manifests, then updates the lockfile.
4. Run the normal operating-system matrix, browser conformance, performance, VSIX smoke, binding corpus, release dry run, and reproducible release gate.
5. Review compiler output, diagnostics, clean and incremental timings, package size, startup behavior, declaration evidence, and source-map mapping evidence.
6. Merge only if all existing release gates and the TypeScript 7 prototype pass.
7. Remove the prototype-only installation step after the committed toolchain uses TypeScript 7; retain the boundary policy and parity checks.

## Rollback

Rollback removes `@typescript/native`, restores the root, CLI, and JavaScript interop `typescript` specifications to exact `6.0.3`, regenerates the lockfile, and runs the stable release gate. The Compiler API import boundary does not change during rollback.

## Consequences

- Virune can use the native compiler without rewriting the synchronous interop provider or binding generator.
- Compiler build performance and Compiler API compatibility can be upgraded independently.
- The repository temporarily carries two TypeScript implementations.
- Package size and install time may increase because native platform packages and the compatibility API coexist.
- Declaration formatting and source-map mapping encodings can change under the native compiler even when generated code, public types, and source references are stable.
- The boundary policy prevents accidental coupling to the legacy API outside the reviewed production and tooling consumers.
